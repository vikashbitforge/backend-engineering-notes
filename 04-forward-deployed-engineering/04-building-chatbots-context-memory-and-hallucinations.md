# Building a Chatbot: Context, Memory, Streaming, and Hallucinations

## 1. Introduction

A chatbot can appear to remember previous messages, follow consistent instructions, and respond naturally throughout a conversation.

However, an LLM call is not automatically a conversation.

A useful chatbot requires application logic to manage conversation history, prepare context, define expected behavior, and handle model responses.

This note explores four important concepts:

- Conversation history and context
- Application memory and system instructions
- Streaming responses
- Hallucinations and reliability

## 2. A Model Call Is Not Automatically a Conversation

Imagine this exchange:

```text
User: My food hasn't arrived.

Assistant: I'm sorry for the trouble.
Would you like to wait or request a refund?

User: I want a refund.
```

To the user, this is one continuous conversation.

At the API level, however, each request can be independent. The model does not automatically receive every previous API call.

If the application sends only the latest message, the model might not know what the user means or which options were discussed earlier.

The application must preserve the relevant history and include it in subsequent requests.

```text
User Message
     ↓
Application Stores Conversation
     ↓
Prepare Relevant History
     ↓
Send Context to LLM
     ↓
Receive Response
     ↓
Store Response
```

**Key principle:** The LLM generates responses; the application creates the conversational experience around those responses.

## 3. Message Roles and System Instructions

Different messages have different purposes.

### User role

Contains the user's request or information.

```text
USER:
My order is delayed.
```

### Assistant role

Represents a previous response generated by the assistant.

```text
ASSISTANT:
Your order appears delayed.
Would you like to wait or cancel it?
```

Previous assistant messages matter because a user's next message may depend on what the assistant said.

### System role

Defines the expected behavior of the assistant for the interaction.

For example:

```text
SYSTEM:
You are a customer-support assistant.

Help with food orders, tracking, payments,
refunds, and company policies.

Be professional and empathetic.
Do not invent missing order information.
```

The system message provides standing instructions, while the user message expresses the current request.

A system instruction influences generation through the context. It does not, by itself, retrain the model or change its learned parameters.

### Instructions are not a complete security mechanism

Prompts can guide model behavior, but they should not replace application-level controls.

Depending on the use case, a reliable application may also require:

- Authentication and authorization
- Input and output validation
- Business-rule enforcement
- Tool and API permission checks
- Structured outputs
- External verification and guardrails

A prompt saying “never perform an unauthorized refund” is not a substitute for enforcing refund permissions in application code.

## 4. Context Window

A context window is the amount of tokenized information a model can process for an interaction, subject to the model's limits.

The context may include:

```text
System Instructions
        +
Previous User Messages
        +
Previous Assistant Messages
        +
Current User Message
        +
Retrieved Information
        +
Tool Results
```

All of this information can influence the model's response.

The model does not respond only to the final sentence. It generates based on the context available to it.

### Context is not model knowledge

These concepts are different:

**Model parameters:** Learned during training.

**Context:** Information supplied to the model during a particular interaction.

If an application tells a model that a project is called `GateKeeper`, the model may use that information when answering a follow-up question, provided the information remains available in context.

This does not mean the model was retrained on that information.

## 5. Conversation History Is Not the Context Window

Conversation history is the sequence of messages stored by the application.

It may be stored in a database, Redis, application memory, or another storage system.

The context window contains the information actually supplied to the model for the current generation.

For example:

```text
Stored Conversation History:
1,000 messages

Context Sent to Model:
System Instructions
+ 20 Relevant Messages
+ Current Question
```

An application can retain a large conversation history while sending only a selected portion to the model.

This distinction is essential when designing chat applications.

## 6. Application Memory Is Not Model Training

Suppose a user tells a chatbot:

```text
My preferred programming language is Java.
```

Later, the chatbot answers a question about the user's preferred language.

One possible implementation is:

```text
User Information
       ↓
Application Memory Store
       ↓
Retrieve Relevant Information
       ↓
Add Information to Context
       ↓
LLM Generates Response
```

The apparent memory can be implemented by the application retrieving stored information and providing it to the model.

This differs from model training, which generally involves updating model parameters using training data.

Therefore:

```text
Application Memory ≠ Model Training
```

This distinction matters when designing personalized applications and explaining what a chatbot actually remembers.

## 7. Why Context Management Matters

Suppose an application includes every previous message in every request.

As the conversation grows, the input can become larger.

A larger input may increase token usage, cost, and latency. It also consumes some of the model's finite context capacity, leaving less room for generated output.

For example, suppose a simplified interaction uses:

- System instructions: 100 tokens
- Each conversation turn: 200 tokens
- Current question: 50 tokens

With 20 previous turns:

```text
100 + (20 × 200) + 50
= 4,150 input tokens
```

This is an illustrative calculation, not a benchmark.

The current question still uses only 50 tokens, but the full request includes much more context.

### Common context-management strategies

An application can select context using approaches such as:

1. Keep the most recent N messages.
2. Keep selected early messages and recent messages.
3. Summarize older conversation history.
4. Retrieve only information relevant to the current question.

Conceptually:

```text
Full Conversation History
          ↓
   Context Management
          ↓
    Relevant Context
          ↓
          LLM
```

**More context does not automatically mean better context.**

The goal is to provide the right information for the current task, not simply the maximum possible amount.

## 8. Context Changes the Response

Consider the same question:

```text
Explain Docker.
```

For a beginner, the application may provide instructions to avoid jargon and use a simple analogy.

For an experienced backend engineer, it may request a concise technical explanation covering containers, images, and operating-system isolation.

The question is identical. The supplied context differs.

That context can influence the generated response without retraining the model.

## 9. Streaming Responses

LLMs generate output progressively. An application can expose the response as it becomes available rather than waiting for the complete answer.

### Without streaming

```text
Client
  ↓
Request
  ↓
Wait for generation
  ↓
Complete response
  ↓
Client displays answer
```

### With streaming

```text
Client sends request
        ↓
Generation begins
        ↓
Response chunks arrive
        ↓
Client displays content progressively
        ↓
Generation completes
```

Streaming can improve perceived responsiveness because users begin seeing the answer sooner.

It does not necessarily make the underlying model generate the complete answer faster.

## 10. Hallucinations: Fluency Is Not Truth

An LLM generates likely continuations based on learned patterns and available context. This process does not automatically verify every statement against reality.

Consequently, a response may be grammatically correct, detailed, and convincing while containing false information.

For example, a model asked about an event that has not happened yet might produce a plausible-sounding account instead of acknowledging that no result exists.

The central distinction is:

```text
Fluent Response ≠ Verified Fact
```

Confident wording is not proof that the information is correct.

Hallucinations can arise when information is missing, outdated, ambiguous, or misleading.

They are especially difficult to detect when fabricated details sound plausible.

## 11. Engineering for More Reliable Responses

A production GenAI application should not rely on the model alone for factual reliability.

Depending on the problem, useful techniques include:

- Retrieval-augmented generation (RAG)
- Search and external APIs
- Tool calling
- Structured outputs
- Input and output validation
- Guardrails and business rules
- Evaluation and monitoring

For example, a customer-support chatbot should retrieve an order's actual status from the relevant system rather than inventing an answer.

If an action requires authorization, the application must enforce that authorization independently of the model's wording.

These techniques can reduce errors and improve grounding, but they do not guarantee zero hallucinations. Reliability needs to be evaluated and maintained.

## 12. Putting the Concepts Together

A more complete chatbot architecture looks like this:

```text
User
  ↓
Application Logic
  ↓
System Instructions
  ↓
Conversation History
  ↓
Context Management
  ↓
Memory / Retrieval / Tools
  ↓
LLM
  ↓
Validation and Business Rules
  ↓
Response
```

Not every application needs every component. The architecture should reflect the actual requirements and risks.

The application determines what information reaches the model, what external capabilities are available, how history is managed, and how responses are handled.

## 13. Key Takeaways

1. An LLM call does not automatically create a continuous conversation.
2. Applications maintain history and supply relevant messages as context.
3. System instructions guide behavior but do not retrain the model.
4. Application memory and model training are different mechanisms.
5. Conversation history and the context window are not interchangeable.
6. Context management affects relevance, token usage, cost, and latency.
7. Streaming delivers generated content progressively and can improve perceived responsiveness.
8. Fluent output is not necessarily factual output.
9. Retrieval, tools, validation, guardrails, and evaluation can improve reliability without guaranteeing perfection.

## Final Mental Model

```text
Store What Matters
        ↓
Select Relevant Context
        ↓
Give the Model Clear Instructions
        ↓
Generate a Response
        ↓
Validate Where Necessary
        ↓
Return a Useful Result
```

**The goal is not simply to make an LLM respond. It is to build an application that gives the model the right context and handles its output responsibly.**
